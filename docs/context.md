## Summary

LineageHeal is a self-healing data pipeline for Indian financial market data. It ingests daily public feeds into a lakehouse and, when data quality fails, uses LLM agents that reason over column-level lineage to locate the root cause and propose a verified fix as a pull request for human approval.

## Problem

India's capital markets serve over 13.6 crore investors holding more than 21 crore demat accounts, and mutual fund assets exceed ₹80 lakh crore (SEBI, 2025). Brokers, fintech apps and research platforms depend on daily public feeds from NSE, AMFI and FBIL, and these pipelines break often. A survey of 200 data professionals reported around 67 data incidents per month and about 15 hours on average to resolve each (Monte Carlo, 2023).

A concrete example: in July 2024, NSE switched to the UDiFF bhavcopy format, changing file names, column names and date formats overnight. Existing data-observability tools detect breaks like this, but diagnosis (tracing the failure back to its upstream cause) still falls to engineers.

## Goals

1. A working pipeline that ingests three public feeds daily into a bronze → silver → gold lakehouse.
2. An agent system that detects failures, localises the root cause using lineage, and proposes a verified dbt patch as a GitHub pull request.
3. A dashboard where a human reviews the incident, lineage path, patch and agent reasoning, then approves or rejects.
4. A reproducible fault-injection benchmark comparing LineageHeal against rule-based and plain-LLM baselines.
5. A research paper based on the benchmark results, written after the system is complete.

## Non-goals

- **Not an investment or analytics product.** Gold tables exist as realistic downstream consumers, not to give financial advice.
- **No autonomous changes.** There is no auto-merge path, ever.
- **No automatic patching outside dbt.** Faults rooted in loaders or sources get a diagnosis and a suggested change, not a pull request.
- **No real-time or intraday data.** End-of-day feeds only.
- **No paid infrastructure.** Everything runs on free tiers.

## Users

| Persona | Need |
|---|---|
| On-call data engineer (primary) | Understand why a pipeline broke and get a correct, reviewable fix quickly |
| Reviewer / approver | Enough evidence (lineage path, diff, test results, reasoning) to trust or reject a fix |
| Data consumer | Gold tables that are correct, or clearly flagged when they are not |
| Researcher | A reproducible benchmark with clear metrics and baselines |
| Demo visitor | Read-only access to explore incidents and fixes without being able to change anything |

## Glossary

| Term | Meaning |
|---|---|
| Bhavcopy | NSE's daily end-of-day market data file |
| UDiFF | Unified Distilled File Formats, NSE's standardised file format adopted in July 2024 |
| NAV | Net asset value per unit of a mutual fund scheme |
| ISIN | International Securities Identification Number |
| Corporate action | An event such as a split, bonus or dividend that changes how prices should be interpreted |
| Bronze / silver / gold | Lakehouse layers: typed raw data / cleaned and conformed data / business-ready tables |
| Lineage | The record of which upstream columns and transformations produce each downstream column |
| Root cause | The upstream source, column or transformation where a failure originates |
| Incident | One detected failure, from detection through investigation, fix and human decision |
| Runbook | A short written procedure for diagnosing or fixing a known class of failure |
| Suggested fix | A drafted change for a root cause outside dbt, filed as a GitHub issue for a human to apply |
| Sandbox | An isolated DuckDB copy where a patch is built and tested before any pull request is opened |

## Fault classes

The benchmark and the agents are designed around five fault classes:

| Class | Example |
|---|---|
| Schema drift | A column is renamed, dropped, reordered or changes type |
| Nulls | Required values arrive blank, e.g. a missing NAV |
| Duplicates | Repeated rows for the same key, e.g. symbol + series + date |
| Unit changes | Values arrive in different units or scale, e.g. paise instead of rupees |
| Late data | A file is missing or arrives after its expected time |

## How the system works

1. **Ingest.** Python loaders download each feed and store the raw file, unchanged, in Cloudflare R2.
2. **Transform and test.** dbt builds bronze, silver and gold models on MotherDuck. Schema tests run on every layer, and anomaly monitors on the silver tables.
3. **Orchestrate.** Dagster models every table as an asset and runs on a schedule in GitHub Actions.
4. **Trace lineage.** OpenLineage events, plus sqlglot parsing of dbt SQL, build a column-level lineage graph.
5. **Heal.** On failure, the Detector opens an incident, the Investigator walks the lineage graph and retrieves similar past incidents and runbooks, and the Fixer writes a dbt patch, verifies it in a sandbox and opens a pull request. If the root cause is outside the dbt project (for example a changed source URL), the Fixer instead drafts a suggested change, shown in the dashboard and filed as a GitHub issue.
6. **Decide.** A human signs in with GitHub and approves or rejects in the dashboard. The outcome is stored for future retrieval.

Full design: `docs/design_architecture.md`.

## Key decisions

| ID | Decision | Reason |
|---|---|---|
| D-01 | FBIL reference rates instead of RBI | FBIL is the current publisher of rupee reference rates |
| D-02 | Raw files stored as published (schema-on-read) | Makes schema drift surface in dbt, where lineage can trace it |
| D-03 | MotherDuck as primary warehouse, local DuckDB for development and tests | GitHub Actions runners are ephemeral, so persistent state needs cloud storage |
| D-04 | Dagster open source, run in GitHub Actions | Free, and its asset model mirrors the lakehouse layers |
| D-05 | Postgres + pgvector on Neon for application state and retrieval | One database for incidents, approvals and hybrid search |
| D-06 | Local open-source embeddings via fastembed | No rate limits, no cost, reproducible benchmark results |
| D-07 | Gemini as primary LLM, Groq as fallback, behind one interface | Free tiers with different rate limits; fallback keeps runs going |
| D-08 | Fixer pull requests are limited to the dbt project | Keeps fixes reviewable and testable with `dbt build` |
| D-09 | Mandatory human approval, no auto-merge | Financial data correctness requires accountability |
| D-10 | React + TypeScript dashboard with a FastAPI backend | Clean separation of UI and API, industry-standard stack |
| D-11 | Benchmark verifies patches in a sandbox on local DuckDB without opening real pull requests; live mode uses MotherDuck and opens real ones | Avoids around 100 throwaway pull requests and keeps the benchmark within MotherDuck's free compute allowance |
| D-12 | MIT licence | Permissive and widely understood for portfolio projects |
| D-13 | Claude Code never commits or pushes; the team commits all changes | Keeps authorship and review with the team |
| D-14 | When the root cause is outside the dbt project, the Investigator still diagnoses it and the Fixer drafts a suggested change as a dashboard entry and GitHub issue, with no pull request | Every pull request stays verifiable with `dbt build`, while source-side faults such as the July 2024 NSE change still get a useful outcome |
| D-15 | dbt Core 1.x (Python) with dbt-duckdb rather than dbt 2.0 | dbt 2.0 shipped in September 2026; Dagster, OpenLineage and Elementary integrations target the Python engine. Revisit after the build. |
| D-16 | API on Render's free tier, dashboard on Cloudflare Pages | Free, Git-based deploys; a cold start of about a minute is acceptable for a demo |
| D-17 | Dashboard login via GitHub OAuth; only allowlisted accounts can approve, everyone else is read-only | Approvals are attributable to a person, and a public demo link cannot merge anything |
| D-18 | Agents open pull requests and issues through a dedicated GitHub App | Bot identity distinct from team members, with narrowly scoped permissions |
| D-19 | The AMFI loader fetches the per-date history report, not the live `NAVAll.txt` snapshot, and bronze selects columns by header name | The live file holds 829 different NAV dates and cannot be fetched for a past date; the two endpoints also name and order columns differently (LH-013) |
| D-20 | NSE history is backfilled in UDiFF only; old-format bhavcopy files (served up to 5 Jul 2024) are the held-out schema-drift case | UDiFF is served back to at least 2 Jan 2024 and matches the old format row for row, so one bronze schema covers the backfill while the old files give ground truth for the replay (LH-012) |
| D-21 | Bronze reads every stored version of a raw file and silver chooses which version to keep | Raw files are write-once and a republished day is a new object, so bronze stays a faithful, append-only view; the version choice needs ingestion times from the ingestion log (LH-014) |
| D-22 | NSE zip files are unzipped into a derived `staged/` area next to the raw zone, and dbt reads from there | DuckDB cannot read zip and raw files must stay exactly as published; staging is deterministic, idempotent, offline and keeps the SQL visible to lineage, unlike a community extension or a Python model (LH-024) |
| D-23 | Development and the mid-project demo run on local storage only; the Cloudflare R2 account (LH-006) is deferred | R2 needs a payment method on file even for its free tier, and the demo does not need deployment. The storage client already supports R2 behind `RAW_ZONE_BACKEND`, so nothing changes in the code when it is switched on |
| D-24 | The ingestion log is optional (no `DATABASE_URL`, no log), but when it is configured a failed write is an error, and files written by fault injectors are logged as stored versions | A silent gap in the log would hide late data and make version selection wrong; keeping it optional means a laptop run needs no database |
| D-25 | Superseded by D-59 on the async question. The store uses synchronous SQLAlchemy | The CLI and loaders are synchronous, and the models and migrations are the same either way |
| D-26 | Silver chooses the latest version of a republished file by the file's modification time, read in SQL from the raw zone, not by querying the Postgres ingestion log | `dbt build`, CI and the benchmark sandbox stay independent of a database, and a metadata-only read is fast; the log stays the authoritative record, to be reconciled with file times (LH-086) |
| D-27 | Gold prices are adjusted only for splits and bonuses, and the published prices stay beside the adjusted close | Splits and bonuses change how many shares a price refers to; dividends do not, so adjusting for them would change what the price means. Rights, demergers and buy-backs are flagged but not adjusted, a stated limitation. Keeping the published columns lets a reader audit the adjustment, and a check proves gold never changes a silver price (LH-026) |
| D-28 | The cross-feed daily summary is not built when either feed fails, and a date missing one feed keeps its row with that feed's figures null and presence flags | A summary with one side wrong is worse than none, and zero would claim nothing traded; the flags separate a weekend from a missing file for late-data detection (LH-026) |
| D-29 | Anomaly monitors are the project's own generic tests (`volume_anomaly`, `distribution_anomaly`, `fresh_within`), not the Elementary package | The spike showed Elementary runs on DuckDB, but its default volume monitor missed a halved file on calendar-shaped data (weekend zero buckets inflate the spread) and its day-of-week seasonality built a wrong training set; the project's monitors compare each date with the same kind of recent dates, read only published dates and never the clock, so they are deterministic for CI and benchmark replays, and need no dependency (LH-027) |
| D-30 | Price and NAV plausibility checks run in two tiers: a scale-sized move with no corporate action fails the build, a smaller but unusual move in the main EQ series only warns | Certainty differs: a hundredfold jump is a unit or scale fault, while a 25 to 30% move is probably real (new listing, suspension, an event the data does not model) and failing the build on it would block every such day; real data showed three such moves in six days, all outside the EQ series (LH-028) |
| D-31 | Dagster runs on a local instance (`dagster_home/`) with raw assets keyed exactly as the dbt sources, and downloads go through code shared with the command line | Asset keys equal to source names let dagster-dbt link raw files to bronze models with no mapping; sharing `ingestion.runner` means a download from Dagster and from the CLI are the same, including the ingestion-log entry; `dagster-postgres` is not added until the Neon database exists, since it needs a second Postgres driver (LH-030) |
| D-32 | The dbt project is one Dagster multi-asset whose run is a `dbt build`; models are keyed by schema and name, grouped by layer, and every dbt test is an asset check | One `dbt build` keeps dbt's own ordering and its skipping of everything downstream of a failed test, which per-model runs would lose; checks show test results next to the asset they guard; dbt is given absolute paths because dagster-dbt starts it in `dbt/`, not the repository root (LH-031) |
| D-33 | Every dbt run's artifacts and a signals summary are kept as files under `runs/<run_id>/` in the raw zone's object store, before the application database exists | Failure signals must be recorded per run now (FR-WH-07, FR-DET-01) but the runs and signals tables belong to LH-036; a file per run is the same record, works locally and on R2, and the database imports it later; a run that fails before dbt writes results still gets a `run_error` signal (LH-034) |
| D-34 | Superseded by D-38 for AMFI and the NSE prices. The anomaly monitors judge a date only when its own pattern (weekday or weekend) has history, and accept it if it is close to either pattern | A weekday market holiday gets a weekend-sized AMFI report (714 schemes against 8,742 on Dussehra 2026), which the weekday-versus-weekend rule called a 92% fault; matching either pattern accepts it while a half-empty file still matches neither; the cost is that a weekday report truncated to weekend size is accepted, which needs the exchange calendar to catch (LH-016, LH-035) |
| D-35 | `backfill` skips days the raw zone already holds, `--refresh` downloads them again, and a day with no file is asked for again | A run of about 2,500 polite requests must be resumable and must not hit the sources for what is already stored; a day with no file may have been published since, whereas AMFI republishes stored days, hence the explicit refresh (LH-035) |
| D-36 | The NSE calendar is a seed of exceptions, each with its source: NSE's official holiday list where it is served, and closures confirmed by asking NSE again where it is not; an official row outranks an observed one and a contradiction is reported, never applied | A calendar derived from the files themselves cannot detect a missing file, because 'expected' would equal 'present'; NSE's API serves only the current year, so earlier years are observed, which the real data justifies (the observed closures matched the official holidays exactly over 2026 up to 23 July); a starred Diwali holiday has a Muhurat session, so a file is expected on a holiday (LH-016) |
| D-37 | The expected-file check judges only the NSE bhavcopy and AMFI, from each feed's first stored file to the run's `as_of_date` (otherwise the newest date any feed has), and warns instead of failing | The corporate actions loader stores nothing for a day without actions and the security master has no history, so absence is not a fault there; starting at the first stored file keeps an unfinished backfill from reading as missing data; a lagging feed is caught by the newest date any feed has, while a run where every feed is late needs `as_of_date`; a warning makes a late file a Detector signal without blocking the layers that did build (LH-089) |
| D-38 | The volume and distribution monitors on AMFI and the NSE prices classify dates by the NSE calendar (business day or not) and judge a date against its own kind only; the seed is declared a parent of the two silver models | The weekday-versus-weekend rule with an either-pattern excuse (D-34) accepted a weekday report truncated to weekend size; with the calendar a holiday is compared with weekend-sized reports and a truncated business day is caught. dbt holds back models downstream of a failed test only when they descend from all the test's parents, so the seed is made a parent of the monitored models or a failed monitor would stop nothing. AMFI is assumed to follow the NSE calendar on regular days only, so a Diwali Muhurat Sunday is treated as weekend-sized, to be checked on real data (LH-090) |
| D-39 | The application schema starts with seven tables (runs, signals, incidents, agent runs, evidence, fixes, reviews) whose lifecycle rules are database constraints, and the knowledge, lineage and benchmark tables are created by the tasks that define them | The Fixer and API are written later and by different code paths, so the database refuses a state the design forbids (a patch published without a sandbox result, a rejection without a reason, a resolved incident without a date); the other tables depend on pgvector, graph versioning and the benchmark runner, so designing them now would mean guessing and rewriting a migration (LH-036) |
| D-40 | The lineage graph is built in memory from the compiled manifest, with a row-set node `<table>.*` per table that filter edges and table-level `inferred` edges attach to, and stored separately (LH-092) | A column used only to filter rows has no output column to point at, and a model that cannot be traced still needs a place for its guessed edges; a row-set node serves both without special cases. Building and storing are split so each stays reviewable, and traversal (LH-040) needs only the in-memory graph. The version hashes compiled SQL with the raw-zone path removed, since that path differs per machine (LH-039) |
| D-41 | The LLM layer calls Gemini and Groq over plain httpx behind a small provider interface, rather than through their SDKs or LangChain model classes; the client owns rate limiting, retries, fallback and structured-output validation | CLAUDE.md already requires httpx with timeouts, tenacity retries and respx mocks; the two REST APIs are simple, a provider SDK would add about 20 packages and hide the retry and rate-limit behaviour NFR-REL-03 needs to control, and agents stay independent of any provider. The interface and client come first, tested with a fake provider and no keys (LH-041); the adapters follow (LH-093) |
| D-42 | Prompts are versioned files checked at load and by a hash lock, and feed data is only ever inserted through a delimiting filter | A typo in a prompt variable would otherwise surface as a silently empty prompt in a live run; recording the prompt id with each run needs ids that never change meaning, which the lock enforces (NFR-MAINT-03, NFR-REPRO-01); feed text such as scheme names is attacker-influenced, so the filter and the sandbox keep it from closing its own delimiter or reaching Python internals (LH-042) |
| D-43 | Provider adapters make one attempt per call and map every outcome to the layer's three errors; a blocked or empty answer and Groq's invalid-JSON rejection count as transient, and Groq uses JSON mode rather than a schema-enforcing mode | Retries and fallback live once, in the client, so a second loop in a provider would multiply waits against free-tier quotas; a block or bad JSON from one provider may succeed on the other, so the client should fall back rather than give up; JSON mode works on every Groq model while schema enforcement does not, and the client validates the reply against the schema anyway (LH-093) |
| D-44 | The stored lineage graph has no `current` flag: the current version is the most recently activated, and only it and the one before it are kept | A flag is a rule two rows could break, whereas an activation time cannot be inconsistent, and saving an old version again (a reverted model change) is just another activation; two versions are enough to compare a change with what it replaced, and the foreign keys make pruning one delete. Incidents do not yet record the version they were diagnosed against, so pruning could remove it: handled with the Detector (LH-092, LH-045) |
| D-45 | Failed downloads become `ingestion_error` signals stored on the run being examined, and a failure stays a signal until a later attempt for the same feed and date ends in anything but a failure, within a one-week window from the run's own time | dbt cannot see a download that failed before it ran, and the ingestion log is the only record; storing them on the run reuses the signal table and its idempotency key with no foreign-key change; a failure that quietly drops out after one run would hide an unfixed gap, while no limit would raise an old backfill gap on every run for ever, and reading the run's time instead of the clock keeps a replay deterministic. A run's status still reflects dbt only (LH-044) |
| D-46 | The Detector groups signals by shared upstream cause leaving filter edges out, fingerprints a group from its root node and its rule-based class, and lets a model refine only the class, confidence and summary of a new incident, with the rules as the fallback | Many models filter on the same calendar, so counting that as a common cause would merge unrelated failures, and the Investigator still follows filters; a model's answer can differ between runs, so putting it in the fingerprint would open a duplicate incident for the same cause, while the rule class never changes for the same signals; detection must not depend on a model being reachable, so rules always answer and a failed call costs nothing but the refinement (LH-045) |
| D-47 | The knowledge index holds one chunk per runbook section with the runbook's title and the section name repeated in the text, records the embedding model on every chunk, skips a runbook by content hash before embedding it, and keeps a namespace on every document | A section is the smallest piece that still reads as advice, and a chunk saying only "check the file hash" matches nothing without the fault it belongs to; vectors only compare within one model, so a changed `EMBEDDING_MODEL` must re-embed rather than mix; skipping before embedding keeps a re-run free; the namespace lets the benchmark use runbooks plus seed-split incidents without ever seeing the incident under test (FR-KB-03). The vector column is pgvector on Postgres and JSON on SQLite, so unit tests stay database-free and only the integration tests exercise search (LH-047) |
| D-48 | Retrieval ranks by position, not score: reciprocal rank fusion (k = 60) over a vector search and a full-text search that matches any query word, each over-fetching 20 candidates; the reranker waits for the benchmark | Cosine distance and full-text rank are on unrelated scales, so fusing by rank cannot let one side drown the other; queries are sentences describing a failure, so requiring every word would find nothing, while the vector side covers paraphrase and the word side exact names such as a column or check; whether a cross-encoder helps is a measurement that needs the benchmark (LH-094). SQLite ranks in Python so unit tests run without Postgres, and the integration tests check the real indexes (LH-048) |
| D-49 | Investigator tools are a closed registry built in code: arguments are validated against a model that refuses unknown fields, a tool that cannot answer returns an error result instead of raising, and the registry itself caps and delimits every output | The model may only choose among registered tools and the values they accept, so no argument can name a path or widen what a tool reads (NFR-SEC-04); an error the agent can read lets it try another route, where an exception would end the investigation; bounding in one place means no tool can forget to; the whole output is cut and wrapped with the existing `untrusted` filter, so feed text in a log line or a scheme name stays data. The calendar tool repeats `slv_meta__calendar`'s rules in Python because the Investigator has no warehouse connection; the data tools that need one come separately (LH-095, LH-049) |
| D-50 | The data tools read the warehouse and raw zone only through one module that opens DuckDB read-only, accepts a table or column only if the catalogue lists it by exact name, and then quotes it; values are bound parameters and a query is interrupted after 5 seconds. The path is a setting (`WAREHOUSE_PATH`), so the benchmark can point it at its sandbox, and `duckdb` is declared as a dependency | Checking names against the warehouse's own catalogue is stricter than checking them against the lineage graph, which lacks tables that were never built, and needs no list kept in step; a read-only connection means a bug in a tool cannot change data; the setting keeps the benchmark's replays from reading the developer's dev file; `duckdb` was already installed through dbt-duckdb, but code that imports it should not depend on another package's dependency (LH-095) |
| D-51 | The Investigator is a plain class with a bounded loop in which a model returns a structured step (one registered tool call, or conclude) rather than using provider tool calling, and its limits and its answer's checks are enforced in code | The LLM layer offers structured output on every provider but not tool calling, and the closed registry (D-49) already validates and bounds every call, so the model only chooses among registered tools; a budget asked of a model is not a budget, so calls (one kept for the answer), seconds, a conclusion that must name a graph node and cite real evidence, a confidence cap when under two findings support it, and a stop that reports the best guess instead of an answer are all enforced in the loop; late data is always external because no dbt change brings back a file (FR-INV-05, FR-INV-06). LangGraph wraps this class in LH-051, so the search stays testable without it (LH-050) |
| D-52 | An investigation is saved by opening a `running` agent run before the search and closing it, its evidence and the incident update in one transaction; a concluded search overwrites the incident's class and confidence, an exhausted one only marks it `unresolved` with a `partial` root cause, and an incident past investigation cannot be reopened | A run that crashes mid-search stays visible instead of vanishing; one transaction means a reader never sees a finished run without its evidence or an incident that disagrees with it; a guess from a stopped search is not evidence enough to replace the Detector's class, but is worth showing a reviewer; once a fix is proposed or a human has decided, a new search must not silently undo that (LH-096) |
| D-53 | The healing graph is LangGraph with two nodes, detect and investigate (a loop over the run's incidents), whose bodies are plain methods over the Detector, Investigator and repositories; the Postgres checkpointer is not added until the review pause exists | LangGraph only decides the order, so everything it runs stays testable without it and the Fixer's branches can be added without touching these nodes; a checkpoint is only needed when a run pauses for a human, and `langgraph-checkpoint-postgres` would add a second Postgres driver for nothing before then, as `dagster-postgres` was deferred in D-31; one crashed investigation is recorded and the others still run, so a bad incident cannot hide the rest (LH-051) |
| D-54 | The Fixer asks a model for the complete new content of the dbt files it changes and computes the diff itself; a model may only change a file it was shown, only existing files under `dbt/models/` and `dbt/macros/` are allowed, and a file too long to show whole is not shown at all | Models often write wrong line numbers and context in a unified diff, and a malformed diff would waste a sandbox attempt, whereas dbt files are small and a diff computed from two texts always applies; showing only what a model may change keeps the path allowlist a second line of defence rather than the only one; a file shown cut short would be rewritten without the part the model never saw, so it is left out; creating new files is not allowed yet, which is a stated limitation (LH-052) |
| D-55 | The sandbox runs `dbt build` on the patched and on the unpatched code, each on its own copy of the warehouse file, and compares every node's status; a node that disappears counts as failing and a build where nothing failed first does not pass | The incident's recorded signals list only failures, so they cannot show what passed before, and a test deleted by the patch must not count as fixed; a fresh before-run costs one more build but uses the same data, code and dbt version as the after-run; whole-file copies are the simplest faithful sandbox and the benchmark can move to copying only the affected tables if the file grows. dbt gets a fixed `PATH` and no inherited environment so a model-written macro sees no credential, and only the `dev` target, so `prod` is unreachable (D-11). The worktree is made from `HEAD`, so uncommitted dbt changes are not in the sandbox (LH-053) |
| D-56 | The GitHub client is plain httpx with PyJWT for the App's signed token, not PyGithub; the App acts for the agents, and approving and merging take an approver's own token per call; branches must be `heal/<incident id>` and committed paths pass the Fixer's allowlist again | PyGithub is LGPL-3.0, hides retries and mocking and needs PyJWT anyway, and D-41 chose the same for the LLM layer; keeping the two identities in separate methods means the bot cannot merge by itself (IF-SW-06) and a merge is attributable to a person (FR-REV-01); checking the branch name and paths in the client as well as the Fixer means a bug upstream cannot write outside the dbt project; a request that may have reached GitHub is never repeated, so a retry cannot open two pull requests; files are committed as one commit through the Git data API from the patch's full new text, which `Patch` now carries because the stored diff alone cannot be committed (LH-054) |
| D-57 | A suggestion for a root cause outside dbt is a `fix` row of kind `suggestion` with its own JSON column, filed as one GitHub issue, and the model is given the diagnosis and evidence but no repository files | The `patch` column holds a unified diff by design and a suggestion is not one; a nullable column is additive and rewrites nothing, and a database rule says a suggestion has content; without file access a model can advise and cannot write something that would be run, so it is told never to invent a path or value the evidence does not show; storing the draft before opening the issue keeps it for the dashboard when GitHub is down, and a retry reuses that row, so there are never two issues for one incident (D-14, LH-055) |

## Constraints

- **Cost:** free tiers only, across all services.
- **Team:** two developers, both on Ubuntu with Docker.
- **Time:** the full build fits in diary Weeks 2–6. The research paper starts after the build is complete.
- **Rate limits:** free LLM tiers cap requests per minute and per day. The benchmark must be designed to run within them, batched and resumable.
- **Warehouse compute:** MotherDuck's free plan includes limited monthly compute, so heavy workloads (benchmark, experiments) run on local DuckDB.
- **Source access:** public sites may throttle or block automated requests. Loaders must be polite and cache aggressively in development.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Source sites block automated or cloud traffic | Ingestion fails in CI | Polite headers and rates, caching, fallback to running ingestion locally and syncing to R2 |
| NSE security master has no history before an unknown date | Backfilled dates may include instruments missing from the master, so silver conformance leaves gaps | Capture the master daily from now on; conform with the latest master and flag unmatched symbols instead of dropping rows |
| RBI blocks automated access to the archive that serves FBIL's rates, or its form changes | The third feed stops arriving; the page is an ASP.NET form with session fields | Polite requests (three per range, three seconds apart, one download for a whole history); fall back to a file downloaded by hand in a browser; the FBIL calendar check (LH-108) reports a gap as late data; if the route is lost for good, agree a replacement rate feed with the guide, keeping the NSE and AMFI feeds as the core of the demo |
| The corpus has no FBIL cases | The benchmark covers two of the three feeds, short of FR-BEN-01 | Add cases when the FBIL loader and an injector exist (LH-020, LH-067); propose the SRS wording to the team if it stays unsolved |
| Free LLM tiers change or tighten | Agents or benchmark stall | Provider abstraction with fallback; benchmark runs batched and resumable |
| MotherDuck compute allowance runs out | Live pipeline paused until the monthly reset | Incremental models; benchmark and experiments on local DuckDB; usage checked weekly |
| Free-tier services pause when idle | Slow first request in demos | Warm-up step before demos; documented in runbooks |
| LangSmith's 14-day trace retention | Older traces unavailable for analysis | Run metrics persisted in Postgres |
| Scope versus five-week timeline | Unfinished features | Weekly milestones in `backlog.md`; core healing loop prioritised over polish |
